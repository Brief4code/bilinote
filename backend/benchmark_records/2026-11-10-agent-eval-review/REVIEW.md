# 视频问答评测复核（2026-11-10）

## 结论与边界

现有实验能支持：在这 5 段视频、40 道固定题及 v1.1 规则下，Agent 配置比单次 RAG 多通过 8 题（29→37），提高 20 个百分点。它是有原始记录的工程回归，但不能据此推导通用准确率、引用可靠性、多轮能力、线上稳定性或整条视频处理链路的质量。

同模型、相同初始检索、失败留在分母、保留评分修订和原始结果，都值得保留。优先补评分有效性和缺失场景，再扩大样本；增加相似题目不能解决测量偏差。

本次只读复核历史数据并离线探测评分器，没有重新调用付费模型，也没有重标全部历史答案。因此下面的评分器反例不等于历史答案实际存在相同错误，不能据此计算一个新的“真实正确率”。历史报告及原始评分保持原样。

## 1. 已复现的评分盲区（最高优先级）

`scripts/evaluate_agent.py:score()` 检查关键词组是否出现，没有验证实体关系、否定、顺序及最终结论。使用 v1.1 的真实题目，以下明确错误的构造答案均被判通过：

| 题目 | 构造答案 | 未检测的错误 |
| --- | --- | --- |
| https-03 | A 记录对应 IPv6，AAAA 记录对应 IPv4。 | 实体对应关系颠倒 |
| fastapi-05 | 先 Execute，再 Try it out。 | 题目明确要求的先后顺序颠倒 |
| resume-04 | 视频没有使用策略模式，也没有使用工厂模式。 | 关键词位于否定句 |
| resume-06 | 原话实际出现在 00:01；15:22 是错误定位，不应该使用。 | 只要出现正确时间就通过，未检查最终主张 |
| fastapi-08 | 视频未提供 P99 的实测数据。不过在1000并发下，接口延迟为30毫秒。 | 拒答后换一种表述捏造数字，绕过禁止模式 |
| https-06 | 时间不是33:20，应该是00:01。 | 被否定的正确时间也算命中 |

运行结果及评分器、rubric 的 SHA-256 见 [scorer_probes.json](scorer_probes.json)。此外，将修复后 37 条通过答案全部加上“下列说法全部错误：”，规则仍判 37 条通过；这只是规则对否定不敏感的探测。

改进要求：

- 对关系、顺序、否定、数值单位、时间与主张的对应关系分别验收；加入正确、错误及部分正确的评分器校准样本。
- 主指标使用盲化人工复核：隐藏配置标签，按题目检查核心事实、矛盾和额外无依据主张；双人独立标注并处理分歧。先复核现有 120 条答案，得到规则误判清单。
- 规则继续作为快速回归指标，单列规则通过率。若引入模型裁判，先用人工标注校准并报告分歧，不能把裁判输出直接视为真值。
- 原文题检查实际引文及归属；所有题型中的额外时间、数字、引用都需要审核，不能只审核时间题。

## 2. 证据进入上下文，不等于回答有可靠出处

当前“证据可得率”只判断标注词组是否进入初始检索或工具返回，既不检查模型是否使用证据，也不检查输出的每个主张是否被支持。无答案题没有标注证据，不在该指标分母内。

当前 `chat_service.chat()` 返回的 `sources` 在工具循环前由初始检索构建，工具取得的新证据没有合并到这个列表。需要针对“初始检索缺失、工具找到答案”的情形，检查最终展示的来源是否确实支持回答。

下一版分别报告：初始检索的标注证据召回、工具补查后的证据召回、关键主张的证据支持率、引用正确率、引用覆盖率、时间定位误差。先明确各项分母，并为允许的替代证据设置人工复核入口，避免固定词组漏判。

## 3. 数据分布与泛化

- 4/5 视频来自同一 UP 主的《零到全栈》课程，另 1 段是技术简历分享；均为 B 站材料。视频约 22–98 分钟，不覆盖短视频及更多内容领域。
- 原文题 5 道、跨片段题 5 道全部给出了目标时间区间。这验证的是已知区间查询，不能代表用户不给位置时的自主查找能力。保留这类题，同时补无时间提示的独立题。
- 所有配置都以空历史开始；没有“刚才第二点”“换个解释”“你说错了”等追问、指代和纠错场景。
- 参考答案来自既有笔记及 ASR/OCR，未经原视频人工核验。笔记和转录发生冲突时，当前实验不能判断谁更接近视频事实。
- 用这 40 题发现问题、修代码再重跑，可以验证回归；由于没有新视频留出集，不能视为独立验收。

建议把现有 40 题保留为开发回归集，另建按视频隔离的留出集。一个可执行的首轮规模是新增 10–15 段视频、100–150 题，分层覆盖题型、内容领域、时长、ASR/OCR 来源和材料质量；这是资源规划起点，不是充分统计效力的保证。题目及评分规则先冻结，避免看完结果再改验收标准。

对用于扩展端到端结论的视频，先人工核验答案相关片段；另外单列转录缺失、识别错误、笔记遗漏与模型回答错误。不要把原材料错误全部归因于问答 Agent。

## 4. 对照、重复与失败归因

现有基线是单次 RAG，Agent 能额外取得完整笔记或更多转录，两者系统提示也有差别。当前初始证据覆盖仅 16/35；Agent 补查后为 32/35。结果包含“取得更多材料”的收益，不能单独归因于工具规划或某一个提示修改。

建议逐步加入以下对照，不必一开始对所有题运行所有配置：

| 配置 | 要回答的问题 |
| --- | --- |
| 现有单次 RAG | 保持历史基线可比性 |
| 扩大检索/重排或同上下文预算的 RAG | 更强检索能否以较少往返取得接近的效果 |
| Agent | 自主补查的收益和代价 |
| 小规模人工提供正确证据 | 失败主要来自找不到材料，还是拿到材料也答不对 |

先在旧题和小规模开发集上选择方案，再在留出集上固定比较。主比较使用同模型同采样设置，另外验证实际生产默认配置；当前生产默认省略采样参数，与历史显式温度 0 的评测不同。

每题每配置至少进行多次独立运行，例如首轮 3 次；保留每次结果，报告翻转率和逐视频/逐题型结果。同一视频的题目相关，重复运行也不增加独立视频数；不应把所有记录简单视为独立样本。需要区间估计时以视频为单位处理聚类，并说明小视频样本的局限。

对照完整性也应补测：报告器比较了请求模型名及部分生成设置，但未强制核对供应商和响应中的实际模型身份；初始检索不同也只是输出 `identical_initial_retrieval=False`，没有拒绝生成报告。后续应把必须相同的条件设置为硬校验，并核对实际模型与运行环境；不能只依赖“同模型”的文字声明。

继续以包含供应商失败的成功率作为主指标，同时补充预先定义的内容错误、检索缺失、工具错误、预算耗尽、供应商失败分类。不要通过只补跑失败题来替换历史主分数。

另需明确：原 Agent 为 38/40，修复后为 37/40。72.5%→92.5% 描述的是 RAG 与修复后 Agent 的配置差异；不能说预算修复使通过率从 72.5% 提升到 92.5%。

## 5. 工具效率与开销

修复后 5 道无答案题全部通过，但进行了 38/87 次工具调用（43.7%），消耗已返回 token 的 68,095/247,954（27.5%）。每题调用 6–9 次工具；3 轮限制并不是最多 3 次工具调用，因为一轮可以有多个调用。

因此 87/87 的工具执行成功只代表返回有效 JSON 且没有 `error`，不代表工具选对、查到新证据或及时停止。需要补：

- 工具名称及参数是否合适、空结果率、重复查询率、新增有效证据比例。
- 单题累计工具调用数、上下文和 token 预算，而不只限制轮数。
- 对无答案题的停止行为：有限查询后正确拒答；对可回答题同步检查过早拒答，防止只靠少查提高效率。
- 对宽时间窗的 50 条截断、完整笔记的 5000 字符截断，检查是否识别截断并缩小查询；这是现有失败 `fastapi-04` 直接暴露的场景。

Agent 已返回 token 为 RAG 的约 4.59 倍，平均时延约 1.67 倍。把质量提升和这两个代价一起报告；后续比较相同预算下的通过率、达到正确答案的调用数，并分题型列出消耗。缺 usage 的请求继续单列，不能按零成本解读。

## 6. 应补的工程场景

| 维度 | 最小测试场景 | 观察/验收点 |
| --- | --- | --- |
| 多轮与历史 | 指代、追问、用户纠错、超过历史上限 | 结论一致、正确利用历史、不串任务 |
| 工具协议 | 未知工具、坏 JSON、参数为列表/空值/错误类型、多工具同轮 | 明确错误、可控恢复、累计预算生效 |
| 工具内容 | 无命中、缺转录、超长返回、50 条/5000 字符边界 | 识别缺失及截断，避免无依据回答 |
| 模型异常 | 403、429、5xx、超时、截断、空正文、关闭工具后仍返回调用 | 失败分类、截止时间、有限恢复、不保存中间结果 |
| 身份与隔离 | 匿名、用户 A 访问 B 的问答/历史/工具材料、删除任务后访问 | 拒绝越权；索引、缓存和来源不泄漏他人内容 |
| 异步任务 | 同 request_id 重复提交、同任务并发、运行中清历史、重启恢复 | 幂等、历史不重复、不跨用户、不遗留运行状态 |
| 索引生命周期 | 未索引、冷启动、材料更新、重建/删除与查询竞争 | 不读旧材料、状态和恢复正确 |
| 材料内指令 | 转录含“忽略用户问题”等内容 | 将其作为待分析材料，不执行材料中的指令 |
| 链路性能 | 冷/热索引、不同并发下排队和端到端耗时 | 排队与执行分别计时，包含失败率和资源占用 |

现有真实评测直接调用 `chat_service.chat(..., history=[], user_id=None)`，绕过路由鉴权、真实历史读取、持久化与异步问答任务。因此即使模型评测全部通过，上表中的产品链路仍需独立集成测试。仓库另有 OCR/并发实验脚本，不能由脚本存在就推断这些问答场景已验证。

## 7. 后端测试与 CI 的实际口径

历史 71 项是当时全部后端测试，涵盖管理员、时间戳、重试、OCR 等，不是 71 项 Agent 专项测试。当前工作区静态发现 86 个 `test_*` 方法，其中评测器/报告 11 个、Agent 预算 4 个；这个计数不代表当前全部执行通过，也不是覆盖率。

`test_agent_chat_budget.py` 用 `skipUnless(find_spec('chromadb'))` 控制整个测试类；CI 只安装 `requirements-ci.txt`，该文件没有安装 `chromadb`，对生产 requirements 的 `-c` 引用只提供版本约束，不会安装依赖。因此按当前 CI 依赖配置，这 4 项关键回归会被跳过。需要设置实际导入成功并执行的 Agent 专项作业，或隔离重依赖使测试可以执行；对关键测试的意外 skip 设置失败检查。

后续报告执行数、通过数、失败数、跳过数，并针对聊天路由、工具、任务及索引模块测分支覆盖；不能以测试数量替代关键行为验证。管理员鉴权已有测试，应补的是聊天链路及工具取数的用户隔离。

## 8. 实施顺序与本次验证

1. **P0：先让指标可信。** 复核旧 120 条答案；加入评分器反例；拆分答案、证据、工具效率指标；保证 Agent 关键回归在 CI 实际执行。
2. **P1：补高价值漏测。** 工具截断与坏参数、异常响应、多轮追问、用户隔离、问答任务幂等和历史一致性。先用隔离临时库和确定性响应离线验证。
3. **P2：再验证泛化与取舍。** 冻结新视频留出集，固定配置后成对重复运行；补更强 RAG 对照、生产配置、并发和冷启动评测，完整报告质量、失败、token 与耗时。

本次验证结果：

- 标准库环境下 11 项评测/报告测试全部通过。
- 完整 `bilinote` 环境下 4 项 Agent 预算测试全部通过，无跳过。
- 不含 `chromadb` 的默认 Python 环境下，同一组预算测试全部跳过，复现了依赖缺失时测试不执行的行为；这是本机模拟，不是新一次远端 CI 运行。
- 评分器 6 个反例全部复现误判，结果保存在 JSON 中。
- 尝试完整后端测试时，执行停留在首项管理员 API 测试，随后主动中断；阻塞原因尚未定位，本次没有取得全量结果，不能沿用历史“71 项全通过”充当本次结果。
